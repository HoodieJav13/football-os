# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

## Durable product design decisions

- The selected editor direction is `option-2-field-focus.png` from the Football OS redesign audit.
- Preserve its layout anatomy: horizontal play-family filmstrip, left edge tool rail, right edge route inspector, and bottom playback timeline.
- Use a refined dark-mode theme derived from the original Football OS drafts. Avoid neon, glow-heavy game HUD styling, photographic turf, scoreboard typography, and floating controls that cover active routes.
- The canvas must remain the dominant region. End Zone is the default view with the offense moving upward; Sideline remains available.
- Touch targets are at least 44 by 44 CSS pixels. Phone support prioritizes viewing and quick adjustments over full editing parity.
- Functional coaching behavior must be real before visual polish: route presets change route geometry, per-player pace is stored on each route, drawn routes persist, temporary game-day changes can be resolved into permanent outcomes, and play thumbnails are generated from each play's actual data.
- The authoring loop supports one pre-snap slot and one post-snap slot per offensive player. Motion occupies the pre-snap slot; route or block occupies the post-snap slot. Defense currently uses one post-snap assignment slot per player.
- A receiver route is structured football data, not just a preset name or arbitrary polyline. Its core definition is release/stem leverage (`inside`, `outside`, `best`, or `none`), stem depth in yards, and one or more break segments with direction, angle, and distance. Double moves are represented as additional ordered break/stem segments. The visible path is generated from this definition, while manual landmarks remain an optional override.
- Route information imported from playbooks must retain its source evidence and confidence. Explicit labels such as `5 YDS`, `12 YDS`, `O/S REL.`, or `SET ANGLE` outrank geometric inference; conditional rules such as man/zone conversions must remain conditions instead of being collapsed into one deterministic path.
- A play can exist temporarily with an illegal alignment only as a clearly labeled draft. Creating a play and explicitly saving play details or a reusable formation require a named, legal 11-player formation; jersey-number legality is not part of this rule.
- Reusable formations store the offensive player labels and alignment, not play assignments. A play created from a formation receives an independent copy that can be edited without changing the saved formation.
- Undo and redo history is scoped to the current play and current editing session. It must never carry an edit across plays or playbooks.
- Treat Personal Active as the user's main working playbook. External source playbooks stay separate, preserve their source terminology and page references, and allow an individual play to be copied into Personal Active as an independent editable play.
- The next visual pass must directly resolve the three audited failures: replace the muddy photographic field with a crisp tactical work surface, make the play browser genuinely useful, and create clear hierarchy across the field, inspector, tools, and timeline without changing the selected Field Focus anatomy.
- The complete core designer assignment vocabulary is offense (`Route`, `Block`, `Motion`) and defense (`Rush`, `Man`, `Zone`, `Fit`). These are structured assignment objects with assignment-specific definitions and generated field geometry, not merely differently styled generic lines.
- Defensive players have stable internal identities that are separate from their visible labels. This is required because multiple defenders can share labels such as `C`, `T`, or `E` without assignments or selections colliding.
- Offense, defense, and assignments are independent canvas layers. Offense and defense can each be shown, hidden, dimmed, or locked; assignments can be shown or hidden. A locked unit remains visible but cannot be moved, relabeled, removed, or have its assignments edited.
- Assignment timing is stored per player as a start delay relative to the snap plus a pace multiplier. Motions default to a pre-snap start; other assignments default to the snap. The animation must honor both values without implying collision or reactive simulation.
- Reusable concepts store assignment stages by stable position label. Applying a concept translates its landmarks to the play's matching position locations. Explicit play-level assignment edits are overrides and must survive a later reapplication of the same concept.
- Production offline status may say `Offline ready` only after the service worker has primed a same-origin application cache. Development/localStorage persistence alone must not be presented as game-day offline readiness.
- Workspace persistence is versioned and migratable. Backup export includes every playbook, play, formation, and concept in a validated `.footballos` envelope; restore requires validation and explicit confirmation, and keeps the replaced workspace as a local recovery copy.
- Coach-facing exports are a clean PNG of the current play and a collection preview that uses the system Print / Save PDF flow. The printable collection follows the active folder/search result when one is present.
- Applying a saved formation translates assignments for matching offensive position labels, removes offensive assignments whose positions no longer exist, preserves the opponent look and defensive assignments, and remains undoable within the current play session.
- Duplicate-as-variation creates an independent editable play linked to the source through `variantOf`; later edits to either play do not silently change the other.
- Play browsing supports folders plus search across play name, family, formation, personnel, protection, and blocking scheme. Swiping the blank field advances within the currently filtered result set so browsing context is preserved.
- On phones, the play browser and canvas layers are compact 44–48px controls that open into temporary panels. They must not permanently consume field height. End Zone/Sideline switching lives inside the mobile Layers panel rather than floating over the canvas.
- The player inspector uses progressive disclosure: player identity, assignment stage, position label, and assignment type are primary; timing, football-specific definition details, and player actions are named expandable sections. On phones it behaves as a two-height bottom sheet with a compact coaching summary and an explicit expanded editing state.
- Every stored coordinate is in yards: `x` is yards right of the field's centre line, `y` is yards downfield of the line of scrimmage. The LOS is the origin, so a route's stem depth and its `y` coordinate are the same number. There is no percentage space and no separate canvas space.
- The canvas renders both axes on one scale, so a lateral yard and a vertical yard are the same length on screen. The visible window is fixed and anchored on the LOS (8 yd behind, 38 yd downfield, at least the full 53.3 yd field width), so every play in a playbook renders at the same scale and is directly comparable. Where the viewport is a different shape from that window, the loose axis is extended to show more field or sideline rather than letterboxed, and never stretched.
- Yard lines, yard numbers, hash marks, and the line of scrimmage are derived from the real field. A yard number states its true distance from the LOS and sits on the line it names; numbers are shown downfield only.
- Inside the box, alignment is drawn to a slightly opened-up diagram convention (interior splits and the defensive front are spaced further apart than reality) because true spacing puts eleven tokens on top of one another. Everything outside the box — receiver alignment, route depth, break distance — is exact. Token sizes are yard-based with pixel bounds so they stay stable at normal zoom and stay separated when the field is zoomed out; hit targets remain a true 44 px.
- Offensive and defensive players share one shape: a stable opaque `id` plus a `label` a coach can change freely. Identity never travels through the label, so duplicate labels are legal on both units and relabelling never rewrites an assignment.
- Assignments live on `play.assignments` (not `play.routes`), reference their player by `playerId`, and always carry an explicit `unit` and `phase` after normalization. Selection is held as an assignment id, never as an array index.
- Workspace persistence is versioned and migratable: v9 introduced yard coordinates, player ids, and the assignments rename. Legacy keys are left in place after an upgrade so it stays recoverable, and a saved play keeps its own alignment rather than being snapped onto the reseeded formations.
- Persistence is debounced rather than written on every state change, because dragging a player updates the play on every pointer move. A trailing write plus a flush when the page is hidden keeps durability without serializing the workspace per frame.
- Every dialog goes through the shared `Modal`: portalled to `body`, closes on Escape and on a scrim click, traps Tab, moves focus in on open and restores it on close, and marks the rest of the app `aria-hidden`. Menus and popovers go through `useDismissable`, which closes them on an outside click or Escape.
- Feedback is tiered. A confirmation is polite and fades; a problem is announced assertively and stays until dismissed or superseded; a reversible action offers undo in place rather than pointing at the undo control.
- Undo and redo are top-level controls in the tool rail, not items inside the overflow menu. Actions that undo cannot reverse are separated from the reversible ones and labelled as such.
- Prevent rather than reject: where an assignment type cannot apply to the selected player, the option is disabled with the reason, instead of accepting the click and answering with a transient message.
- The drawing tool stays selected after a stroke so several assignments can be drawn in a row; Escape returns to Select.
- Keyboard support is a requirement, not an extra: tool keys, undo/redo, arrow-key nudging, delete, playback, play stepping, and Escape. Shortcuts never fire while a text field has focus or a dialog is open.
- A global shortcut outranks a focused control's own convention where the two collide. Tokens carry `role="button"` but deliberately do not activate on Space, because Space is run/pause and clicking a player focuses its token — activating on Space swallowed the most-used shortcut in the app for the rest of the session, silently, since re-activating an already-selected token does nothing visible. Enter alone gives the keyboard its way in. Starting a run remounts the canvas to restart `animateMotion`, so focus is put back on the token afterwards; without that, previewing a play cost a keyboard user 23 Tab presses.
- Player tokens are real controls, not decoration: each `<g>` carries `role="button"`, a spoken label naming the unit, the alignment and the assignment, and a plain `tabIndex` so Tab walks the whole roster. Nudging and deleting were already on the keyboard, but nothing could reach a player to nudge in the first place — the tokens are the entry point that made the rest usable. A locked layer drops to `tabIndex={-1}` so Tab skips what a pointer also cannot touch.
- Which axis binds the canvas decides where layout effort pays off, and it differs by device. A phone in portrait is width-bound, so trimming chrome buys no field at all. Desktop and a phone in landscape are height-bound, so vertical chrome is expensive and surplus width is nearly free — which is why the landscape phone puts every control in the side columns, and why the desktop inspector widens rather than the canvas.
- The inspector pins the player's identity and assignment stage and scrolls only the detail editor, so changing a route never scrolls away the context that says whose route it is. The body carries this further: it is a column of fixed rows plus one elastic one, so the open section takes the leftover height and scrolls inside itself and the collapsed summaries stay on screen. The editor's content is a fixed ~659px whatever the window size, so scrolling the body as a whole hid the Timing and Player actions summaries entirely on an ordinary laptop.
- SVG has no z-index, so on the canvas paint order and tab order are the same list read once. That makes layer order a compromise, not a free choice: offence is placed before defence so a coach reaches their own eleven on the first Tab, accepting that a defender paints over an offensive player where they overlap — which no seeded play does, the units being 2.5 yd apart with a largest token radius of 0.72 yd. Route handles go last because they are draggable.
- Play thumbnails frame their own play rather than the whole field. Drawn through the fixed window they sat near 2.4 px/yd filling under half the card, which made variants of one family indistinguishable and the browser useless for the job it exists to do.
- Playback moves the tokens themselves, not proxy dots. The players run their assignments via `animateMotion` with paths expressed relative to each token's alignment (`tokenMotionPath`) — an absolute path would displace an already-positioned token by its alignment again. Labels rendered outside their token's group carry the same animations separately. The old dots stood all twenty-two players frozen while half-yard dots slid around, which was accurate but nothing like watching a play.
- Dragging is magnetic rather than gridded: positions move freely (rounded to a tenth of a yard) but click onto another player's row or column, or the LOS, inside `ALIGN_SNAP_YARDS`. Alignment in football is relative — "stack behind Z", "same depth as F" — so the magnets are players, not grid lines, and every snap draws its guide through the player that caused it plus a live spot readout ("12.3 R · on LOS"). Alt drags free. The LOS outranks a row magnet for offensive players.
- The canvas has a camera: `fieldProjection` takes an optional `{ factor, centre }` zoom in field yards, clamped inside the base framing so panning reaches everything that was visible unzoomed and nothing more. Pointer math flows through the same projection, so drawing, dragging, and snapping work at any zoom with no special cases. Zoomed in, an empty-field drag pans (projection frozen at pan start so the delta cannot chase its own centre); at base framing the same gesture keeps its swipe-between-plays meaning.
- Switching plays morphs the board instead of hard-cutting: the SVG is deliberately not keyed by play id, matched tokens FLIP-glide between alignments, and routes fade in behind them. Player ids are unique per play, so matching uses unit + label + occurrence index ("the second defensive T"). The morph is skipped whenever the window itself moved between plays (a fitted view refits per play, so user-unit deltas would lie about on-screen motion), during playback, and under prefers-reduced-motion. Every play switch forces playback idle, which is what makes the shared SVG safe: no SMIL timing survives a switch, and runs restart by remounting via runKey alone.
- The timeline is a real slider over one SVG time container: press or drag anywhere on the track (or arrow-key it) and `setCurrentTime` scrubs every token at once. Scrubbing from idle enters *paused* playback -- the animations only exist while playback is live, so the target time is parked until the remounted SVG is in the DOM -- and scrubbing while running pauses, because grabbing the playhead means "stop it right there". The playhead paints straight to the DOM once per frame; a React state update at 60Hz would re-render the whole app to move a 10px dot. Its predecessor was a decorative 3.2s CSS animation with no relationship to the play's real duration.
- Thumbnails diff against the family's base play (first of the family in full library order, stable under filters): routes the variant changes pop in accent, shared ones recede. The tolerance is deliberately coarse (2 yd) because in real families shared routes drift by a yard of re-spacing while the route a variant is about goes somewhere else entirely -- a tight tolerance flagged everything and emphasised nothing. Cross-play identity is the same unit|label|occurrence scheme the morph uses (`morphKeys` in playData).
- Break depths render like an install sheet ("@12"), Route-type only -- blocks and motion have no depth vocabulary -- behind a toggle in the Key popover because they are reference detail, not always-on signal.
- The app shell is split by surface: `Header`, `Filmstrip`, `ToolRail`, `LayerBar`, `Inspector`, `Timeline`, `PlayDialogs`, `Feedback`, `SegmentedControl`, with shared pure helpers in `appHelpers.js` and the zoom/pan camera in `useCanvasCamera.js`. `App.jsx` keeps only orchestration: state, the actions that mutate a play, and composition. Panels take props and hold no workspace state, so a surface can be read on its own.
- Motion is a system, not per-feature: three duration tokens (120/200/320ms) and two curves, applied so nothing user-visible changes state without a transition. Entrances carry the smoothness (modals scale over a fading scrim, popovers grow from their trigger, the inspector slides in, the phone sheet rises); exits stay instant by design because animated exits would need unmount management everywhere. Layers stay mounted when hidden and crossfade, dropping pointer events and tab stops. The first-load roster stagger is gated by a ref that only counts after the canvas has size, so it never replays on the SVG remounts that runs and view changes cause.
- Depth is directional: chrome shadows point at the canvas so the field reads as the recessed work surface; the field itself is lit (radial lift, edge vignette, LOS glow) rather than filled; offensive tokens cast shadows while defenders stay deliberately flat, which encodes the unit hierarchy without colour. Screen-space grain lives on the stage as a tiled CSS background, not an SVG filter in field space, so it rasterises once and never re-renders on pan or zoom.
- Solid routes draw themselves (dash-offset reveal, staggered) on load and play switch; dashed assignments fade instead because a dash reveal would destroy their pattern mid-animation. During playback each route brightens for exactly the window its player runs it, driven per-frame from the SVG clock rather than CSS delays so it stays truthful through pause and scrubbing.
- Present mode slides chrome off its own edge while grid rows/columns collapse, so the field glides to fullscreen; sliding avoids the overflow clipping that a shrinking row would need, and visibility flips after the ride so off-stage controls leave the tab order.
- Pointer affordances live on the token group and its hit circle, not the visible circle: the 44px hit target extends past the drawn token, and a cursor that reverts to `auto` in that ring says "not interactive" exactly where a press would land. The hover halo fills the true hit area, so what lights up is what a press will grab.
